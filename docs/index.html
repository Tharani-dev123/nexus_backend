Payroll & Tax Declaration API

A multi-tenant backend service for managing company payroll runs, salary structures, employee records, and India-style income-tax declarations (Old & New regimes) with an admin approval workflow and employee self-service portal.

Node.js Express 5 TypeScript Prisma 7 PostgreSQL JWT Auth AWS S3 + SES v1.22.0

What this service does

The platform is organized around companies. An authenticated user creates a company and becomes its root user. Within that company they manage departments, employees, salary structures and monthly payroll. Employees (and admins) then file annual tax declarations that the engine computes against configurable tax-regime slabs.

👤 Identity & Auth

Sign-up, email verification, JWT access/refresh tokens, multi-device session management, password reset.

🏢 Org Management

Companies, departments and employees with role-based and company-scoped access control.

💰 Payroll

Spreadsheet upload, parsing & validation, payroll runs/entries, salary-structure projection, pay statements.

🧾 Tax Declarations

Self-service investment declaration, Old/New regime computation, proof uploads, admin approval workflow, Excel exports.

Startup & lifecycle

  • src/index.ts — entry point; boots the HTTP server on PORT (default 3000) and registers graceful shutdown.
  • src/server.ts — Express app: helmet → cors → request-id → context → device-info → request logger → cookie-parser → body parsers → routes under /api → 404 & error handlers.
  • src/utils/shutdown.ts — handles SIGINT/SIGTERM, runs cleanup, force-exits after a 10s timeout, and traps uncaught exceptions / unhandled rejections.
All application routes are mounted under the /api prefix. Every full path in the API reference below is therefore /api/<module>/<route>.

Authentication

The service uses a dual-token JWT scheme: a short-lived access token for API calls and a long-lived, database-backed refresh token for session continuity and revocation.

TokenLifetimeStoragePayload
Access token12 hours (43,200s)Client only (Bearer header)user_id, company_id?, rftoken_id, expiresTime
Refresh token30 days (2,592,000s)SHA-256 hash in RefreshToken tableuser_id, type: "refresh"

How it works

  • Login validates the password (bcrypt) and the isEmailVerified flag, then issues both tokens. The refresh token's hash is persisted; the access token carries a reference (rftoken_id) to that DB row.
  • Every protected request passes through auth.middleware.ts: the Bearer access token is verified, its rftoken_id is checked against the DB to confirm the session has not been revoked, and the user (plus company, if any) is attached to req.user / req.company.
  • Refreshing (/auth/refresh-access-token) verifies the refresh JWT, looks up its hash, validates it is unexpired and unrevoked, extends its expiry, and mints a new access token.
  • Logout revokes the current refresh token by setting revokedAt; logout-all-devices revokes every active token for the user.
Pass the access token as Authorization: Bearer <token> on all routes except the public auth endpoints.

Authorization

Beyond authentication, two company-scoped guards control access. Most non-auth modules require a companyId query parameter that is validated against the caller's access.

GuardEnforces
authenticateUserValid, non-revoked access token; populates req.user
authorizeCompanyAccessCaller is the company's root user or a member of the company (via companyId)
verifyCompanyRootAccessCaller is the company's root user — required for mutating/admin actions

Roles are modeled by the UserRole enum: OWNER, ADMIN, HR, EMPLOYEE.

Middleware, Logging & Integrations

  • Request context — AsyncLocalStorage carries request_id, IP, and (after auth) user_id / company_id through async calls for correlated logs.
  • Device info — ua-parser-js extracts browser/OS/device for session and audit context.
  • Logging — Winston (JSON, with stack traces) plus Morgan HTTP logs; optionally shipped to BetterStack/Logtail. Console output is colorized.
  • AWS S3 — getObject / deleteObject back payroll spreadsheet ingestion and tax-proof document storage.
  • AWS SES — transactional email built as MIME via Nodemailer (with CID-embedded social-media images) and sent through SES v2.
  • In-memory cache — a small TTL cache backs email-verification and forgot-password OTP flows (5-minute expiry).
  • Audit log — the AuditLog model records actor, action, entity, old/new values, IP and user-agent.

Salary Structure Engine

A salary structure maps an employee's annual CTC onto a set of components. Because some components depend on others (HRA on Basic, balancing on everything), the engine (calculateSalaryStructure) resolves them in a fixed multi-pass order.

1 · FIXED / %CTC / %GROSS→ 2 · %BASIC→ 3 · FORMULA→ 4 · BALANCING→ Deductions
Calculation typeResolved as
FIXEDA literal annual amount
PERCENTAGE_OF_CTC% of annual CTC
PERCENTAGE_OF_BASIC% of the resolved BASIC component
PERCENTAGE_OF_GROSS% of resolved annual gross (used for deductions)
FORMULAExpression referencing earlier component codes and CTC
BALANCINGCTC minus all other earnings (max one per structure; earnings only)

Output is a SalaryBreakdown: per-component annual & monthly amounts, annual/monthly gross, annual deductions and net. Monthly figures are rounded to two decimals to avoid floating-point drift. Validations enforce a positive CTC, a single balancing earning, and non-null values where required.

Payroll Processing

Payroll is ingested from spreadsheets stored in S3. The flow turns a raw sheet into a validated, itemized PayrollRun.

  1. Fetch & parse — parsePayrollSheet reads the Excel/CSV from S3, detects the header row (employee-code column + ≥2 component columns) and normalizes headers via a COLUMN_MAP.
  2. Resolve — component column codes map to master PayrollComponent ids; employee codes map to Employee ids. All codes are validated against the company roster.
  3. Derive — LOP = days − effective workdays; deductions are aggregated by type (PF, ESI, income tax, professional tax, other); gross/net are computed and cross-checked against any provided totals (mismatches surface as warnings).
  4. Persist — atomically create the PayrollRun + one PayrollEntry per employee with itemized PayrollEntryComponent rows. With replace=true an existing run for the same period is swapped; otherwise a duplicate period raises a 409 conflict.

A pay statement (payStatement) returns a year-wise view that combines actual entries with a projection for missing months. Projection basis is chosen in priority order: LAST_REGULAR_PAYROLL (latest completed Regular payroll) → STRUCTURE (active salary structure) → NONE. This annualized view feeds the tax engine.

Tax Calculation Engine

calculateTaxDeclaration computes income tax for a declaration against a versioned TaxRegimeConfig (slabs, surcharge bands, cess rate, caps) for the selected financial year and regime.

  1. Salary derivation — deriveSalaryFromPayroll folds pay-statement components into declared buckets (BASIC, HRA, conveyance, medical, special, communication, bonus, other) and extracts professional tax & TDS.
  2. HRA exemption — least of: rent paid, 50% (metro) / 40% (non-metro) of gross, and 40% of basic.
  3. Standard deduction — regime-specific (e.g. ₹50k Old / ₹75k New).
  4. Chapter VI-A — items aggregated per section with statutory caps (80C ₹1.5L shared ceiling, 80CCD(1B) separate, etc.); HRA & home-loan handled separately. Most deductions apply to the Old regime only.
  5. Taxable income — gross − exemptions − standard deduction − Chapter VI-A + other income.
  6. Tax — progressive slab tax, then surcharge by income band, then 4% cess.
  7. Rebate 87A — applied automatically when income is under the regime threshold.
  8. Balance payable — total tax − TDS already deducted.

The result is persisted onto the TaxDeclaration and rendered by buildTaxWorkingSheet into a JSON working sheet (Decimals coerced to numbers).

Declaration Lifecycle

Each declaration moves through a small state machine. While DRAFT, salary figures are auto-refreshed from payroll on every read so the employee always declares against current numbers.

DRAFT→ submit → SUBMITTED→ approve → APPROVED
SUBMITTED→ reject → REJECTED→ edit → DRAFT
StateBehavior
DRAFTEditable; salary refreshed on read; investment items fully replaceable (proofs carried forward FIFO)
SUBMITTEDSalary frozen at submission; awaits admin decision; edits blocked
APPROVEDImmutable; records approver & timestamp
REJECTEDCarries a rejection reason; re-opening reverts it to DRAFT for resubmission
Tax data (slabs, caps, standard deduction, rebate thresholds) is seeded per financial year & regime via TaxRegimeConfig, so computations stay accurate as budgets change without code changes.
